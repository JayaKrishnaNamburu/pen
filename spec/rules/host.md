# Host Integration Rules

The `HOST` family owns the contract between Pen and the application that embeds it: module-graph safety, framework client boundaries, the declared runtime floor, feature detection above that floor, server rendering, and the styling contract. Pen's own tests always run in the environment Pen was written in, while every environment a consumer ships into — a React Server Component build, a server-side render pass, an older Safari, a phone on a plain-HTTP LAN address — is a separate promise. These rules exist to make each of those promises testable rather than asserted, which is the difference between a library that works and a library that works here. Pen ships no polyfill bundle, no shipped theme, and no CSS-in-JS dependency; it detects and degrades, and the floor tells a host which polyfills to bring.

## HOST — host integration

- HOST1. Every module in `@input/pen-react` that a consumer can import and that uses React client hooks carries `"use client"`, placed on the package's entry points and on each subpath entry rather than scattered per component. The build must preserve the directive in both ESM and CJS output, and that is a build-output assertion rather than an intention: the gate greps `dist/`. `@input/pen-vue` needs no directive but documents the same client-only mount stance, while `@input/pen-core`, `@input/pen-types`, and the non-rendering extensions stay directive-free and importable from server code — which is what HOST2 protects.
- HOST2. No published module touches `window`, `document`, `navigator`, `matchMedia`, `localStorage`, `getComputedStyle`, or `requestAnimationFrame` at module scope; browser access happens inside functions, effects, or lazily-initialized accessors, enforced by the `no-module-scope-browser-globals` lint. Import safety is tested rather than asserted: a smoke suite generated from the manifests imports every path in every published `exports` map in a plain Node process with no DOM globals and fails on any throw, and because it is generated, a new package or subpath is covered the day it exists. The same suite asserts that `createHeadlessEditor()` constructs and applies ops in that process, which turns the headless claim into a test instead of a hand-verified habit.
- HOST3. Every published package declares `engines.node` matching what CI verifies, and CI runs a matrix across the declared range's endpoints rather than only the version the maintainer uses, because a floor is a promise. A single browser-support table is published in the README and the docs site and is the normative floor for the whole workspace: minimum Chromium, WebKit and Safari, and Firefox versions, with the EditContext-versus-contenteditable backend split stated per browser, since that split materially changes input behavior. The floor is derived from the features the code actually needs — HOST4's allowlist is the inventory it comes from — rather than chosen aspirationally; raising it is a minor-version change with a changelog entry, and lowering it never happens silently. `spec/` and the docs site state the floor identically: one number, one place, referenced everywhere else.
- HOST4. Above the floor, detect; at or below the floor, use freely, because a guard for a guaranteed feature is noise. Any web API newer than the HOST3 floor is used behind a feature test with a defined degraded path and a documented consequence for the user, and the inventory of above-floor APIs is a lint with an allowlist (`scripts/above-floor-api-allowlist.json`, rule `no-above-floor-api`) where each entry names its fallback — that list is what the HOST3 floor is derived from, which keeps the two honest about each other. ID generation in library code goes through one helper (`generateId`) that owns the feature test and the fallback, and bare `crypto.randomUUID()` calls in published packages are banned by the `no-bare-random-uuid` lint: a missing UUID API may degrade ID quality but must never prevent constructing an editor, including on a non-secure origin such as plain HTTP to a LAN address. Library-authored inline styles and stylesheets either sit at the floor or carry a fallback declaration in the same rule (`background: <fallback>; background: color-mix(...)`); a visual nicety may degrade, but a highlight that vanishes may not, so the AI review surfaces in particular must stay visible without `color-mix()`.
- HOST5. Server rendering has a stated contract, and the choice is shell-only SSR: the server renders the editor container and no document content. That is deliberate rather than accidental, because faithful SSR of a CRDT document requires the document on the server and Pen does not own that transport. A host needing indexed content renders it from its own copy of the document through the DOM-free HTML export surface rather than from the editor, and the docs show that pattern — the difference between "SSR is unsupported" and "SSR renders a shell, and here is how you get content into HTML". Layout effects run through one `useIsomorphicLayoutEffect` seam so a server pass produces zero React warnings, and zero is the gate because hosts read warnings as bugs regardless of who caused them; hydration is tested with both an empty and a non-empty document, asserting no mismatch for the shell.
- HOST6. Pen is headless: it ships no required stylesheet, and an editor with no CSS is functional — editable, caret visible, blocks laid out by the host. Functional includes an empty document, which is the case that separates a stated contract from a tested one: an empty `[data-pen-inline-content]` has zero width, so pointer activation resolves the clicked `[data-pen-editor-block]` rather than only the inline span, and a host is not required to supply a `min-width` to land the first keystroke. Where the library must style something for correctness rather than taste — caret overlays, selection highlights, focus rings (AX5, with overlay carets staying `aria-hidden` per AX7), suggestion decorations — it does so through inline styles or a documented, overridable custom-property surface, and every custom property the library reads is documented with its default and its purpose, canonically in `packages/rendering/react/STYLING.md` and `packages/rendering/vue/STYLING.md`. Boolean `data-*` attributes are presence-only: `true` emits the valueless HTML form (`data-readonly=""`), `false` and `undefined` omit the attribute, hosts style with the bare selector `[data-readonly]`, and `buildDataAttributes()` in `@input/pen-dom` is the single producer, re-exported by `@input/pen-react`; off must be absence rather than a false-y value, and ARIA booleans are exempt from this convention because they stay the literal strings `"true"` and `"false"` — `aria-hidden=""` is invalid and matches nothing.

## Retired

No `HOST` member is retired. HOST1–HOST6 are all live and govern shipped code.
