# Documentation And Adoption Surface

Pen is an MIT-licensed SDK evaluated by teams who read the docs before they read the code, so the adoption surface is part of the product rather than a courtesy around it. This document owns everything an adopter reads first: the quickstarts, the docs site, the generated API reference, per-package READMEs, runnable examples, and the release trail. It governs the root `README.md`, `packages/*/README.md`, `packages/docs`, `examples/`, `playground/`, and the release workflow.

## DOC — Documentation and adoption surface

- DOC1. One complete quickstart per supported host — React, Vue, and vanilla `@input/pen-dom` — lives in the root `README.md` in full rather than as a link to a sub-package, because the root README is where evaluation starts. Each states the exact install command including peer dependencies, the imports, a mounted editor, where styling comes from in one sentence, and the client-boundary note for App Router hosts. Quickstarts are executed in CI rather than proofread: each exists as a minimal app under `examples/`, a job installs from built workspace artifacts, builds it, and asserts the editor mounts and accepts typed text, so a drifted quickstart fails the build; package names and versions named in prose must resolve in the workspace, checked by a doc gate.
- DOC2. The docs site publishes the full content set or does not deploy at all — a live URL reading "coming soon" tells an evaluator the project is abandoned, which is worse than a 404. The minimum content set, each page owned by a spec document so it cannot rot independently, is getting started per host, core concepts (blocks, ops, `editor.apply`, origins), the selection model, extensions and facets, commands and keymaps, collaboration setup, AI features, import and export, security posture for embedders, the accessibility statement, browser and Node support, localization, and upgrade guides. Every code sample on the site is type-checked, either extracted from compiled fixtures or checked in place, and the site links the generated API reference instead of restating signatures in prose, because hand-copied signatures drift and generated ones cannot.
- DOC3. The public API of every published package is documented by a reference generated from the same API reports that enforce the public/internal boundary — one source, two consumers — and generation fails on an undocumented public symbol, which is what makes this rule real rather than aspirational. Every exported symbol carries a TSDoc one-line summary, exported functions document parameters, return values, and thrown conditions, and exported option objects document every field's default. Diagnostic codes and message keys are published as reference tables generated from their frozen definitions, since hosts subscribe to diagnostics and override messages and both need enumerable lists, and the reference is versioned with the release train with the previous major left reachable.
- DOC4. Because npm renders the package README as the package's front page, each published package's `README.md` states what the package does and what it does not do, the install command including peer dependencies, a minimal working usage snippet, its options with defaults, links to the docs page and the API reference, and the license line; a doc gate checks the required sections per published package. Packages that are meaningless alone say so in the first sentence and name the package a consumer should install instead — that is a complete README, since the contract is honesty about scope rather than length. Extension READMEs additionally document the facets and commands they contribute and the extensions they depend on, because that is what a consumer assembling a preset needs and cannot get from types alone.
- DOC5. `examples/` contains one minimal app per supported host plus one per headline capability — collaboration with two clients on one document, AI with a model adapter and transport wired to a stub, and import/export — where minimal means the smallest thing that runs, since an example is read rather than extended. Examples install Pen the way a consumer does, through workspace artifacts standing in for registry versions, and never through relative source imports into `packages/`, because an example that reaches into the source cannot catch a packaging break, which is half of what examples are for. `playground/` is the reference app and the host for the end-to-end suite: it is `private: true`, it carries AI server code, and it is documented as neither an example nor a supported starting point; the root `README.md` links a hosted try-it target so evaluation does not require a clone.
- DOC6. Per-package changelogs are generated by changesets and committed, and every release train is tagged, because a consumer pinning a version needs to read what changed without reading commits. There is no migration guide: nothing has been published, so no consumer has a prior version to migrate from, and what a host assembling from this repository needs to know is onboarding rather than upgrade guidance — it belongs on the docs site and in the per-package READMEs that DOC2 and DOC4 already require. No deprecation period and no one-minor deprecation window is published, because that window is unnecessary on a `0.x` line and was never opened. The support policy (which `0.x` lines are supported and for how long, plus the security-report response expectation), the distribution channel described accurately once (registry, access level, and how to get credentials when access is restricted), issue and pull-request templates, and CODEOWNERS routing are all published rather than left archaeological.

## Retired

No `DOC` member is retired. DOC1–DOC6 are all live and govern shipped code.
