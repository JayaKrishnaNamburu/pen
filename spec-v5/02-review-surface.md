# v5 Review Surface: One Preview (RS)

Status: adopted 2026-08-26. `RS` rules are normative. This document consolidates the six mechanisms that can put AI content in front of a user (`00-concept.md` §2 fact 5) into three surfaces with three jobs, and makes the styling of the surviving surface a single exported contract. The review surface's payload semantics (what an in-flight preview may show, EC-verified plain text, posture totality during streaming) are owned by the `EC` rules in `spec/packages/extensions/ai.md` where already specified; RS owns the consolidation and the host-facing contract.

## 1. The Surfaces

- RS1. **Three surfaces, three jobs, no fourth.** After Wave 2 the only ways AI content reaches a user's eyes are: (a) the **visible stream** — `openTextStream` typing into a streaming target the user watches (generation into empty or appended targets, continuation, selection rewrite in direct mode); (b) the **autocomplete ghost** — the inline completion overlay, which previews a keystroke-accepted completion, not a document edit; (c) the **review surface** — streaming preview text while an edit is in flight, staged suggestion decorations once it lands, for every proposed edit regardless of lane. Adding a fourth surface requires demonstrating an edit-presentation job none of the three can express, in a spec amendment, before code.
- RS2. **Every proposed edit rides the review surface.** The selection-rewrite suggestion decorations and the buffered markdown block preview — today two bespoke presentation stacks with their own lifecycles — migrate onto the review surface: selection rewrites stage as ordinary suggestions rendered by the review presentation; block generation previews render as streaming preview blocks and then stage. The suggest-mode staging interceptor is the single staging authority; the host's mutation preference (`suggestions` vs `direct`) decides whether an edit stages or applies, and has no effect on _which_ surface renders it while pending. The two bespoke stacks are deleted in the same wave their consumers migrate (WA9).
- RS3. **Posture is total, including the end of a session.** Every state a reviewable edit can occupy renders a defined posture: in-flight (streaming preview text), awaiting review (staged decorations with accept/reject), resolving (accept/reject application), and terminal (resolved away). No reachable state renders nothing. A generation that ends with edits neither applied nor staged must surface that fact to the host (the unapplied-edit report shipped in the better-ai train is the mechanism; RS3 makes it a standing obligation covering every lane that can propose an edit, not just the loop).
- RS4. **One styling contract, exported once.** The review surface's class vocabulary is defined in one module and consumed everywhere: the four sites that today each import review style constants (`suggestionDecorations.ts`, `streamingPreviewVirtualDecorations.ts`, `reviewPresentationStyles.ts`, `contextDecorations.ts`) collapse onto one exported sheet with CSS custom properties as the theme seam. Hosts theme by setting custom properties; they do not re-implement rule blocks. The playground's hand-rolled copies in `playground/src/editor/editor.css` are replaced by the exported sheet plus property overrides, and both binding styling docs (`packages/rendering/react/STYLING.md`, `packages/rendering/vue/STYLING.md`) point at the same contract instead of telling each consumer to write their own.
- RS5. **Preview text is plain text with no control tokens.** The streaming preview renders exactly what will land — already verified for the tool channel — and no marker vocabulary survives the XML teardown: `MARKDOWN_FAST_APPLY_OMISSION_MARKER` (`runtime/flowMarkdown.ts:16`) and any other channel-control token die with the channel (UC1). A preview that needs to say "content omitted here" says it through the presentation layer's own affordance, never through magic strings in the payload.
- RS6. **Preview fidelity is measured, not presumed.** The corpus comparison harness keeps a fidelity check: for every corpus edit, the text the preview showed equals the text accept applies, per operation. A fidelity regression fails the wave gate. This is the property that made the tool channel's preview honest — it must keep holding as the other lanes migrate onto the surface.

## 2. Consequences

The mechanisms deleted by RS1–RS2, named so the diff is checkable: the selection-rewrite bespoke decoration stack (its staging survives; its presentation folds into the review surface), the buffered markdown block preview renderer, and the markdown-preview-specific plumbing in the generation-execution path. The visible stream and the ghost overlay are explicitly kept: they are not previews of proposed edits — one is watched generation the user asked to land as it types, the other is a keystroke-gated completion — and forcing them through review posture would break both jobs.

## 3. Testing Contract

- RS1: a presentation-inventory test: drive each lane in a headless host and assert the rendered surface is one of the three (the test enumerates decoration types present; an unknown decoration type fails).
- RS2: migration tests per lane — selection rewrite in suggestions mode stages through the interceptor and renders review decorations; block generation renders streaming preview blocks then stages; the deleted stacks' decoration classes appear nowhere.
- RS3: a posture-totality test walking a reviewable edit through every state and asserting a non-empty defined posture at each step, plus the end-of-session unapplied-edit report for a non-loop lane.
- RS4: a styles test asserting all review decoration class names resolve from the single exported vocabulary; a grep gate that the four legacy constant sites are gone; playground builds without its hand-rolled review rules.
- RS5: a grep gate that the omission marker token appears nowhere in `packages/`; the preview plain-text tests from the better-ai train keep claiming their EC rules.
- RS6: the corpus fidelity assertions in the comparison harness, run as a wave exit gate.
